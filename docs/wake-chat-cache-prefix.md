# Wake/chat prefix consistency

Production inspection on 2026-11-26 (UTC timestamps) found the same primary SDK Session across both modes. At 04:53:16 a wake used 207870 total input tokens, reading 205065 from cache. The 05:00:55 foreground request used 213650 input tokens but read only 768. Its tool list changed from 83 to 89: six shared-calendar definitions returned, and mail_send changed its schema/description. System bytes changed from 21444 to 21394 characters, diverging at character 9159 because autonomous mail restrictions were substituted into the system prompt. The following consecutive foreground request previously recovered a normal cache read. Same Session was insufficient to preserve cache when these prefixes differed.

Harness routes now retain the normal chat's full tool definitions during autonomous turns. Calendar definitions remain visible for prefix stability, but no autonomous calendar execution handler is registered. Mail schema/description remain stable; executeMailTool still enforces owner-only/no-CC autonomous sending. The exact autonomous mail instruction moves to a wake-only user suffix. Original persona and Markdown prompt files remain byte-identical. Existing API-provider behavior, mode-specific output budgets, compaction policy and Session restore remain unchanged. Output limits varied even across cache-hitting wakes, so this patch does not change them.

A new full HTTP/scheduler/SDK fixture exercises normal chat -> persisted/restarted scheduled silent wake -> normal chat. It asserts complete system/tool byte equality and same Session, while attempting forbidden wake calendar access and foreign-recipient mail. It also verifies no silent chat bubble and the wake-only mail suffix. Existing stream, image, memory, compaction and real pinned-SDK localhost tests remain in the regression set. All model traffic in validation is local/synthetic; no live Kimi probes are sent.

Cache hits and retention remain provider-controlled. The first request after a changed prefix or application compaction may need a fresh cache write; stable modes prevent the demonstrated avoidable invalidation, but do not establish a one-hour TTL.
